## E. 硬體 QoS（QDMA）：主線（延後開發，先做漫遊中控）

軟體 SQM（cake）對 MT7621 負擔太大（PPPoE 下大約 400 Mbps 就到頂），改以晶片內建的 QDMA 硬體排程為主線。
**同一個韌體**內建，後台切換「關閉／固定／自動」，不另外出版本；每個機型只有標準版與 OC 1000 版。

決定：
- 沿用 Padavan 原本的 hw_nat 驅動（田野使用最多），**不放雙驅動**、不移植 padavanonly 的 mtk_hnat
- 硬體排程與硬體 NAT 同時運作：封包依標記進 QDMA 佇列，由排程器限速，CPU 幾乎不參與
- 設定只寫在記憶體，不為了自動化寫 Flash
- 軟體 SQM 已從韌體移除（`configs/tw/common.config`），程式碼保留在 `trunk/user/sqm-qos`

| # | 項目 | 狀態 |
|---|---|---|
| E1 | hw_nat 執行中開關：`/sys/module/hw_nat/parameters/hnat_qos`、`hnat_qos_wlan`；後台設定 `hw_qos_*`（模式、Wi-Fi、方案頻寬、傳輸技術、上限 +%、下限 −%） | ✅ |
| E2 | 驗證工具 `tw-qos-check`（status／on／off／limit／clear／watch／guide）與 `/proc/mt7621/qdma` 狀態頁 | ✅ |
| E3 | 實機驗證（D3）：兩個方向、有線與 Wi-Fi 是否都經過 QDMA；開排程的效能損失；小封包延遲 | 🔬 **等實機** |
| E4 | 固定模式：依方案頻寬 ×（1 + 上限%）限速，方向用 iptables 標記（單一 GMAC 機型上傳下載同一張網卡） | 📋 |
| E5 | A、B 兩種做法都做成後台選項 `hw_qos_method`（預設 A）：A＝自動模式時排程一直開，只調速率（不用清硬體表）；B＝需要時才開排程並清表。E3 實測後再決定預設值 | 📋 |
| E6 | 自動模式控制器（見下方流程） | 📋 |
| E7 | 學習：記錄每次介入的時段、ping 起伏與結果，學到的壅塞時段提早介入；只存記憶體 | 📋 |
| E8 | 後台「頻寬管理」頁：模式、方案、傳輸技術、上下限；目前狀態與最近介入紀錄 | 📋 |
| E9 | 遊戲／語音優先佇列：小封包、低速率的 UDP 放到優先佇列 | 🔬 |
| E10 | 軟體 SQM 從韌體移除（連同 QoS 排程、IFB 核心選項） | ✅ |
| E11 | 中華電信 MOD（IPTV）流量不經過排程 | 🔬 |

### 自動模式流程

平常完全不介入（硬體 NAT 全速）；只在「延遲變高而且頻寬真的快用滿」時介入，不需要時自動關閉。
上限、下限以「申裝方案頻寬」為準，預設上下對稱 ±15%，可手動調整。

| 狀態 | 檢查 | 動作／離開條件 |
|---|---|---|
| ① 平常 | ping 每 10 秒 | 延遲比基準高 30 ms 以上，且 WAN 流量 > 方案 70% → ② |
| ② 確認中 | ping 每秒，共 10 秒 | 10 次中 7 次偏高 → ③；否則回 ① |
| ③ 控制中 | ping 每秒 | 從上限（方案 +15%）開始限速，延遲仍高就逐步往下調，最低到下限（方案 −15%） |
| ④ 判斷 | 每次調整後 30 秒 | 延遲改善 → 停在這個速率；降到下限還是沒改善 → 塞車不在我們這段，慢慢加回上限後結束控制、回 ①，30 分鐘內不再因同樣狀況介入 |
| ⑤ 結束 | 每 5 分鐘 | 連續 3 次流量 < 方案 50% 且延遲正常 → 解除限速回 ① |

保護：每小時最多介入 4 次；介入與解除都寫入事件時間軸（D5），後台看得到原因與前後延遲。

已確認（維護者）：上下對稱 ±15%；加回上限就結束控制；觸發條件「延遲偏高＋流量 > 方案 70%」；A／B 做成選項。
